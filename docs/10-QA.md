# 10 — QA

## 1. Propósito

Definir la **estrategia de pruebas** de Visual Library **antes** de implementar código de producto: pirámide, alcances, criterios de aceptación y gates por fase.

---

## 2. Objetivos de calidad

1. **Invariantes de dominio inviolables** (Library gate, plan approved, etc.).  
2. **Jobs durables** ante crash/reinicio.  
3. **SQLite + FS** coherentes.  
4. **Flujos MVP** verificables E2E con provider stub.  
5. **Regresión barata** en CI local/GitHub.  
6. **No falsa confianza** por tests solo de UI superficial.

---

## 3. Pirámide de pruebas

```
        E2E (pocos, caros)
      --------------------
      Integration (SQLite, FS, jobs, IPC smoke)
    ------------------------------------------
    Application use cases (ports fake/in-memory)
  ------------------------------------------------
  Domain unit tests (políticas, transiciones)
--------------------------------------------------
```

| Capa | % esfuerzo relativo | Velocidad | Dueño |
|------|---------------------|-----------|-------|
| Domain unit | alto | ms | `crates/domain` |
| Application | alto | ms–s | `crates/application` |
| Integration | medio | s | `infrastructure` + temp dirs |
| E2E | bajo | decenas de s–min | `packages/ui` + app |

---

## 4. Pruebas unitarias (dominio)

### 4.1 Qué probar

| Área | Casos |
|------|-------|
| Asset transitions | approve/reject/duplicate solo desde waiting_review; approve desde rejected falla |
| Plan gate | automatic permitido solo approved |
| Found policy | match exacto; no match; exclusion blocks; no considerar non-approved |
| Coverage targets | under/over detection pure functions |
| Exclusion rules | scope global/concept |
| ConceptRelation | parent cycle detection (si aplica) |

### 4.2 Qué no probar aquí

- SQL  
- Tauri  
- HTTP providers  
- React components  

### 4.3 Criterio

Toda invariante de [02-DOMAIN.md](./02-DOMAIN.md) §10 tiene al menos un test negativo y uno positivo.

## 5. Pruebas de dominio / application

Use cases con **repositorios en memoria**:

| Use case | Escenarios |
|----------|------------|
| Manual preview | lista → FOUND/GENERATE decisions |
| Manual submit | encola generate solo faltantes |
| Automatic run | falla si plan draft; ok si approved |
| Approve | asset sale de waiting; search library lo encuentra |
| Reject | library no lo encuentra |
| Regenerate | nuevo request + no auto-approve |
| Export info | solo approved ids |

Assertions sobre llamadas al `JobQueue` fake (qué se encoló).

---

## 6. Pruebas SQLite

### 6.1 Scope

- Migraciones en DB vacía (todas las versiones).  
- FK y checks básicos.  
- Repos reales: insert/get/list filtros.  
- Claim de jobs concurrent-safe en serialización.  
- Queries de coverage under-covered con fixtures.

### 6.2 Técnica

- Temp directory por test.  
- Aplicar migraciones desde cero.  
- No depender del DB del desarrollador.

### 6.3 Casos mínimos

1. migrate_latest_on_empty  
2. asset_review_queue_order  
3. library_search_excludes_waiting  
4. found_candidate_query  
5. job_claim_returns_one  
6. plan_items_by_priority  

---

## 7. Pruebas filesystem

| Caso | Expectativa |
|------|-------------|
| write_atomic | archivo final existe; tmp limpio |
| path traversal | `../` rechazado |
| missing media root | error accionable |
| generate stub writes file | path relativo en DB resuelve a bytes |
| export copies only approved | rejected no se exporta |

Usar directorios temporales; nunca el media root real del usuario.

---

## 8. Pruebas de Jobs

| Caso | Expectativa |
|------|-------------|
| echo job completes | status completed |
| crash while running | al reboot → interrupted → requeue/fail |
| cancel queued | no side effects |
| generate idempotent | segundo handle no duplica asset |
| materialize draft plan | fail |
| max_attempts | failed terminal |

Simular crash: marcar running y llamar recovery sin ejecutar handler completo.

## 9. Pruebas E2E

### 9.1 Principios

- Provider **stub** (sin red ni costos).  
- Dataset fixture pequeño.  
- Cubrir el **camino crítico** del MVP, no todos los edge UI.  
- Estables (esperas por estado, no sleeps ciegos cuando sea posible).

### 9.2 Escenarios E2E canónicos

| ID | Escenario | Criterio de paso |
|----|-----------|------------------|
| E2E-01 | Shell muestra 6 estaciones | nav completa |
| E2E-02 | Settings guarda media root | persistido tras restart app (si harness lo permite) |
| E2E-03 | Manual preview FOUND | muestra found sin generate |
| E2E-04 | Manual generate → Review | asset en waiting, no library |
| E2E-05 | Approve → Library | visible en search library |
| E2E-06 | Reject → no Library | search no devuelve |
| E2E-07 | Plan draft no corre Auto | error visible |
| E2E-08 | Plan approve → Auto → Review | assets waiting |
| E2E-09 | Coverage lista under-covered | issue visible con fixture |
| E2E-10 | Job recovery | (semi-E2E/integration) job no perdido |

### 9.3 Herramienta

- Preferir harness Tauri + driver disponible en el stack elegido.  
- Si E2E desktop es costoso al inicio: **API-level E2E** (use cases + sqlite + fs + stub) como gate, y UI E2E cuando el shell esté estable.

---

## 10. Criterios de aceptación por flujo (producto)

### Factory Manual

- [ ] Lista inválida se rechaza con errores por fila.  
- [ ] FOUND no crea asset nuevo.  
- [ ] GENERATE crea waiting_review.  
- [ ] ExclusionRule produce SKIPPED.  

### Factory Automatic

- [ ] Solo plan approved.  
- [ ] No hay generación sin items.  
- [ ] Items no fulfilled hasta approved targets.  

### Review

- [ ] 5 acciones del MVP operan con precondiciones.  
- [ ] Transiciones ilegales fallan.  

### Library

- [ ] Solo approved.  
- [ ] Export no incluye rejected.  

### Coverage

- [ ] Responde las preguntas canónicas con fixtures.  
- [ ] Issues tienen CTA lógico (tipo/code).  

### Plans

- [ ] Approve habilita automatic.  
- [ ] No side effect de media al aprobar.  

### Settings

- [ ] Path inválido detectado.  
- [ ] No expone acciones de producción.  

### Jobs

- [ ] Estados durables y recovery.

## 12. CI / gates

### 12.1 En cada cambio de código (cuando exista)

1. `cargo test` (workspace)  
2. lint/format Rust  
3. frontend unit si hay  
4. integration sqlite/fs  

### 12.2 No bloquear por

- Snapshots visuales pixel-perfect (no existen aún)  
- Providers reales de pago  

### 12.3 Gate de fase

Ninguna fase del plan se marca **Done** sin:

- pruebas listadas en esa fase en verde  
- criterios de terminado de la fase  

---

## 13. Bug severity (para futuro triage)

| Severidad | Ejemplo |
|-----------|---------|
| Blocker | Asset en Library sin approve |
| Critical | Job perdido tras crash; plan draft genera |
| Major | FOUND incorrecto; coverage miente |
| Minor | copy UI; sorting |
| Nit | estilo código |

**Policy:** Blocker/Critical impiden release de fase de features afectadas.

---

## 14. No-goals de QA (MVP)

- Chaos multi-host  
- Penetration test completo  
- Performance a 10M assets  
- Compatibilidad con todos los OS en día 1 (definir targets: Windows first dado el entorno actual; macOS/Linux en matriz posterior)  

**Target OS inicial propuesto:** Windows (dev actual), diseño portable.

---

## 15. Definition of Done (global de una feature de flujo)

1. Use cases + tests application/domain.  
2. Persistencia y tests sqlite/fs si toca I/O.  
3. Command IPC + manejo de error.  
4. UI mínima de la estación (sin scope extra).  
5. Criterios de aceptación del flujo en checklist.  
6. Docs actualizadas si cambia una decisión.  
7. Sin violación de NON_GOALS.
